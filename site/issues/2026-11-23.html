Scope the agent before it starts

The safest agent is not the one that promises never to make a mistake. It is the one whose identity, permissions and stopping conditions make a mistake small.

1. AWS gives agents a narrower identity primitive

AWS introduced GetScopedCredentials in STS on November 20. It derives new temporary credentials from an existing session, but only with permissions that are the intersection of the caller's effective permissions and an inline scope-down policy. The derived session can also be shorter-lived, and the operation can be chained so an orchestrator gives each sub-agent an even narrower identity. AWS Security Blog.

The important design choice is that the model never needs to receive the parent role. A trusted broker can translate task context into a policy, mint credentials for one worker, bind them to one tenant or resource prefix, and let AWS enforce the boundary even if the agent chooses the wrong tool.

Why this matters: Authorization becomes a runtime property of the task, not a promise embedded in the prompt.

2. A leaked credential turned an agent mistake into a data incident

On November 21, Together AI disclosed that an AI coding agent committed a credential for a private Hugging Face repository into a public GitHub repository. Automated scanning caught and reverted the commit, but an unauthorized party obtained the credential during the exposure window and downloaded stored prompt samples. Together says its investigation is ongoing and that it has strengthened credential, pull-request and AI-agent controls. Together AI incident report.

The practical lesson is not merely “use secret scanning.” Keep build and test agents away from production credentials, prefer short-lived or keyless access, require pull-request checks, and assume that a credential can be copied before a revert lands. Rotate from a clean environment and inspect access logs when exposure is possible.

Why this matters: Fast rollback limits repository history, but it cannot rewind a credential that was already read.

3. Long-running agents need a clock and a wait state

OpenAI published a pattern for personal agents that must finish work by a deadline while sometimes needing clarification. The application adds a fresh time reminder before every model request, keeps a deadline fixed, and lets an asynchronous question wait for user input without blocking the rest of the run. OpenAI Developers.

For engineering workflows, apply the same pattern to migrations, release preparation and incident research: record the deadline, persist checkpoints, make side effects idempotent, define what happens when the user never answers, and expire authority independently of the model session. A run that reaches its deadline should produce a bounded handoff—not keep spending because the agent still has tokens.

Why this matters: Timeouts and unanswered questions are normal workflow states; treating them as exceptions makes recovery harder.

4. Secret detection is moving into the agent loop

GitHub's November 17 update lets Copilot's security-review specialist run GitHub secret-scanning detectors alongside its existing analysis in Copilot CLI, the Copilot app, SDK integrations and Copilot code review. GitHub says the preview covers more than 500 secret types, but the feature is off by default, and SDK integrations need GitHub authentication rather than only a model-provider API key. Scans consume credits under the Secret Protection AI Credit SKU. GitHub Changelog.

Enable it where your agent creates or reviews code, then keep an independent repository-level secret-scanning check as a merge gate. Treat both tools as detection layers, not permission to expose secrets to the model. Test false positives, fork behavior, generated files and logs before making the result blocking.

Why this matters: Security review is stronger when deterministic detectors and model reasoning inspect the same change—but neither replaces credential isolation.

Tool spotlight · AWS STS GetScopedCredentials

What it does: It narrows an existing temporary AWS session to a smaller policy and/or a shorter remaining lifetime. Best use: a trusted credential broker issues task-specific credentials to an agent, sub-agent or CI worker only after the task and resource scope are known.

  1. Start with a read-only task such as “summarize objects under this S3 prefix.” Give the broker a parent role that cannot delete data.
  2. Have the broker construct a scope-down policy for the exact bucket prefix and required actions. Replace wildcards with concrete resources wherever possible.
  3. Call sts:GetScopedCredentials with the temporary parent credentials and request a duration shorter than the parent session.
  4. Pass only the derived credentials into the isolated worker. Do not pass the parent credentials, and do not let the worker call the broker unless chaining is explicitly required.
  5. Log the task ID, authenticated principal, policy hash, duration, resource scope and worker outcome. Add a test that a second tenant or destructive action is denied.

Important caveats: the API only narrows permissions; it does not make a bad policy good. AWS notes that generated policies may contain broad wildcards, so review and tighten them. The broker is now a high-trust component and must authenticate task context instead of accepting a model-generated identity claim. Keep credentials out of prompts, traces and shell history, cap retries, and monitor for policy-construction bugs. API reference · Implementation guide.

Why this matters: The best agent permission is the smallest credential that can complete the next verifiable step.

Today’s practical takeaways

  1. Inventory every credential an agent can read, inherit or mint; remove ambient access before adding more autonomy.
  2. Put a broker between agent intent and cloud credentials, and make its policy output inspectable and testable.
  3. Add a deadline, checkpoint and no-response path to any run that can outlive a single interaction.
  4. Run deterministic secret scanning on agent-created changes, then rotate anything that may have crossed the boundary.
  5. Measure successful, reviewed outcomes—not agent activity—and include security checks, retries and human time in the cost.

Start with one low-risk repository task today. Give the worker one resource scope, one short-lived identity and one acceptance test. If the task cannot prove what it changed and what it was allowed to touch, it is not ready for a wider permission set.
