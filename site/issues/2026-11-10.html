Make agent access explicit

The next reliability problem for agentic software is not only what a model can do. It is whether the surrounding system makes identity, permissions, source boundaries, and tool contracts visible enough to review.

1. Google is turning “agentic” into an OAuth property

Google’s Workspace developer notes say OAuth clients calling Workspace MCP servers must be marked Use this client for an AI-powered agent. Starting November 11, 2026, unmarked clients will be rejected; clients that remain unmarked by November 12 will stay unable to call the MCP servers. The change covers preview MCP servers for Chat, Docs, Drive, Sheets and Slides, while ordinary REST API integrations are not affected.

Before tomorrow, inventory every OAuth client that can reach Workspace through MCP. Separate agent clients from non-agent clients when one credential currently serves both, then test the authorization path in a staging project. Record the client ID, intended agent, scopes, data sources and human approval point in the repository.

Why this matters: An agent’s identity and permissions are part of its behavior; if they are implicit, a harmless prompt can still reach the wrong data boundary.

2. Web search is becoming an infrastructure decision

AWS has added the InvokeWebSearch API to Bedrock AgentCore. Code you own can call the API with AWS SDKs or the CLI, filter by domains and publication dates, and receive ranked results with extracts, URLs and publication times. AWS also documents a gateway connector for MCP agents, where target-level domain lists can be applied outside the calling agent.

That split is useful: use the API when your application owns retrieval, and the gateway connector when an agent discovers tools through MCP. In both cases, keep the returned citations, restrict domains for high-consequence workflows, and test what happens when sources are stale, contradictory or unavailable. AWS says the API requires IAM and is available in six regions; the gateway connector has different regional and authorization details.

Why this matters: Current information is not automatically trustworthy information; retrieval policy, source retention and failure handling belong in the system design.

3. Typed tools reduce ambiguity at the model boundary

The OpenAI Node SDK v7.55.0, released November 10, adds typed async function tools. The release also updates development dependencies, including Zod. Typed schemas do not make a tool safe by themselves, but they make arguments, validation and return handling easier to inspect in code review.

Use the new capability for one read-only function first. Define a strict input schema, reject unknown properties, validate authorization inside the function, and return structured errors that the agent can reason about without being given hidden credentials or raw stack traces. Add tests for missing fields, cross-tenant identifiers, timeouts and repeated calls.

Why this matters: A clear tool contract gives your evaluator something concrete to test—and gives reviewers a place to see where the model’s authority ends.

4. Security coverage must include the agent’s workbench

Forrester’s November 5 analysis of agentic-development security argues that coding agents need controls beyond generated-code scanning: they select dependencies, invoke tools, execute tasks and can affect the delivery environment. Its evaluation of 12 providers across 29 criteria found no single vendor strongest across every current capability, and warned teams to distinguish shipped features from roadmap promises.

Translate that into a small internal test matrix: prompt injection through repository files, unauthorized tool calls, dependency substitution, secret exposure, unbounded network access and unsafe retries. Run it against the same agent configuration you use in development—not just against a model in isolation. Treat findings as control gaps to fix, not a leaderboard to admire.

Why this matters: Agent security is a workflow property spanning code, tools, credentials and deployment—not a badge attached to the model.

Tool spotlight · released November 10

OpenAI Node SDK v7.55.0

What changed: The JavaScript/Node SDK added typed async function tools, making it easier to define model-callable functions with a typed contract while keeping execution in your application.

Try it: Upgrade a sandbox project, choose one read-only operation such as getBuildStatus, define its input with a strict schema, and log four fields for every call: requesting agent/session, validated arguments, authorization decision and result status. Add a test that passes an identifier belonging to another tenant and verify the tool rejects it before any external read.

Caveats: SDK typing is compile-time and validation is only as strong as the runtime checks you keep. Do not move authorization into the prompt. Review dependency changes, pin versions where reproducibility matters, and measure the full loop—tokens, tool latency, retries and human review—not just model latency. The release is current as of this edition and may be superseded quickly.

Why this matters: Typed tool boundaries turn agent behavior from “the model said so” into an inspectable, testable interface.

One thing to try before lunch

Create an agent access card for one production-adjacent workflow: identity, allowed tools, data domains, write permissions, network policy, timeout/retry budget, human approval point and revocation procedure. Ask a teammate to review the card against the actual OAuth scopes, tool code and runtime configuration. If the card cannot describe the workflow, the workflow is not ready for broader autonomy.
