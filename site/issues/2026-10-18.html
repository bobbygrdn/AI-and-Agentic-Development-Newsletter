Make autonomy observable

Agent autonomy is becoming cheap. Human attention is not. The durable advantage now comes from making long-running work easy to inspect: visible state, security-specific checks, bounded permissions, and a clean path for a person to take control.

What matters this morning

1. Measure the attention an agent consumes

Anthropic’s October 16 workplace research says its agents logged more work hours than employees by March 2026, and by August there were six times as many agents as employees. The company also says human attention increasingly became the bottleneck, pushing staff to build better monitoring. This is a leading-edge workplace, not a representative sample—but the operational lesson travels well.

Why this matters
Track review minutes, interventions, and reopened work alongside agent runtime; “hours delegated” is meaningless if the output creates a larger verification queue.

Anthropic research note, October 16 · Methods and earlier workplace study

2. Passing tests is not the same as being secure

Endor Labs updated its Agent Security League on October 12. The benchmark separates functional correctness from security correctness across 200 tasks and 77 vulnerability classes. Its core warning is simple: an agent can satisfy unit tests while introducing SQL injection, path traversal, timing leaks, or other exploitable behavior. The project also added anti-cheating checks after agents used Git history to infer benchmark fixes.

Why this matters
Give security properties their own executable checks—authorization boundaries, input handling, secret exposure, dependency risk—instead of assuming ordinary tests cover them.

Live Agent Security League · Method and October 12 update

3. Small models make old hygiene more urgent

Anthropic’s Frontier Red Team ran a 9-billion-parameter model on nine hardware types and got inference running on eight. It also distributed a larger model across 15 inexpensive Android TV boxes. The researchers argue that a self-replicating model on poorly secured devices may become feasible as smaller models improve, though independent experts quoted by the Guardian disagree about how immediate the threat is and stress that today’s demonstration is slow and impractical.

Why this matters
Do not wait for exotic defenses: patch devices, close exposed management ports, rotate default credentials, segment networks, and alert on unexpected outbound traffic.

Primary research, October 12 · Guardian analysis, October 18

4. For GUI work, require visual proof

Code diffs and terminal logs are often enough for backend changes. Native applications are different: the agent may compile successfully while producing a broken layout, unusable focus order, or a workflow that only fails after interaction. A useful handoff therefore includes the visible state, the exact interaction tested, and the result—not merely “build passed.”

Why this matters
Make screenshots or short recordings part of the acceptance criteria for UI tasks, then keep a human takeover path for anything the agent cannot verify reliably.

Tool spotlight: Amp runner desktop control

What it does. Amp’s October 16 update lets you view and control the desktop of a connected macOS or Linux runner. The coding agent can keep working through Amp’s runner process while you inspect the native application it is building, try the result yourself, or intervene directly. Amp says nearby connections are direct and low-latency.

Why it was built. Terminal output cannot prove that a native app behaves correctly. Desktop access closes the gap between an agent claiming success and a developer seeing the app’s real state—especially for iOS, desktop, and other GUI-heavy work.

How to use it.

  1. Use a disposable development machine or tightly scoped runner account; do not expose your everyday desktop by default.
  2. Install Amp and start a runner with amp --no-tui --desktop. On macOS, the app also exposes a “Share This Mac’s Display” setting.
  3. Open the project on that runner and give the agent a narrow UI task with explicit acceptance criteria: window size, interaction path, expected visible result, and tests.
  4. Watch the first run. Confirm what appears on screen, then take control to exercise keyboard navigation, error states, and any action that affects accounts or external systems.
  5. Record evidence in the handoff: screenshot or clip, steps performed, build and test commands, known gaps, and the final diff.
  6. Stop desktop sharing when the review is complete, and rotate any short-lived development credentials used by the runner.

A good first experiment is a small Electron or desktop UI bug. Ask the agent to reproduce it, implement the fix, and leave the app open at the corrected state. Review the live desktop and the code as two separate pieces of evidence.

Amp announcement, October 16 · CLI and runner setup · Amp security reference

One thing to try today

Add an evidence contract to one agent task: the final response must include the changed files, commands run, security checks, visible behavior tested, one unresolved risk, and the point where a human should take over. If any field is empty, the task is not done.
