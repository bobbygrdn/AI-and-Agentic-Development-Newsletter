Build the agent as a software project

The most reliable agent is not a clever prompt hidden in a demo. It is a small, versioned project with typed tools, repeatable evaluations, and a deployment boundary you can inspect.

1. Make the agent’s behavior legible in the repository

Cursor’s new Agent SDK models an agent as a folder of code: instructions, tools, skills, connections, channels, and evals. Even without adopting that SDK, the design is worth copying. Keep the agent’s operating instructions, tool contracts, fixtures, and release notes beside the application code so a teammate can review what changed.

Why this matters
Versioned agent behavior turns “the bot got weird” into a diff you can inspect, test, and roll back.

2. Give every tool a typed boundary

Use one file or module per action, with explicit inputs, outputs, and failure states. Keep model judgment separate from deterministic code that validates identifiers, checks authorization, formats requests, or performs writes. A tool should make the safe action easy and the ambiguous action visible.

Why this matters
Typed boundaries reduce the number of ways a model can translate a vague intention into an unsafe side effect.

3. Turn real incidents into eval fixtures

An eval should assert more than the final sentence. Check which tools ran, with what inputs, whether the agent asked for clarification, and whether it avoided an approval or write action when conditions were not met. Cursor’s SDK supports replaying real GitHub pull-request webhook payloads into a bot, which is a useful way to convert production surprises into regression cases.

Why this matters
Every fixed failure should become a permanent test so the next model or prompt change cannot quietly reintroduce it.

4. Design deployment as a change in trust

Local playgrounds are for iteration; hosted agents need a clear account of secrets, egress, sessions, logs, and data retention. Decide which tools can run in development, which require approval in staging, and which are prohibited in production. Run the same eval suite against the deployed agent before enabling event triggers.

Why this matters
Deployment changes what the agent can reach, so production readiness is a systems question—not just a passing demo.
Tool spotlight · newly released

Cursor Agent SDK

What it does: Cursor’s Agent SDK lets developers define agents as code, run them locally with a playground, test them with evals, and deploy them to Cursor-managed infrastructure or their own infrastructure. The project structure includes an instructions.md file, typed tools, on-demand skills, MCP connections, and channels for GitHub, Slack, webhooks, and scheduled events.

Why it was built: Teams were building recurring agents for code review, security review, approvals, incident work, and other lifecycle tasks, but each new agent could otherwise become a one-off product. Cursor built the SDK to make those agents manageable like ordinary software projects, using the same harness behind its managed agents while keeping the workflow customizable.

How to use it: Run npx @cursor/agent-sdk init ./my-bot, then use agent-sdk dev to start the local playground. Add the smallest useful typed tool set, create evals that check tool calls and replies, run agent-sdk validate, and deploy with agent-sdk deploy only after the local behavior is repeatable. If the agent reacts to GitHub events, use replay fixtures and keep write tools guarded during evaluation.

One thing to try before lunch

Take one existing prompt-based automation and create four folders: instructions, tools, evals, and fixtures. Move one deterministic action into a typed tool, write three evals for success, ambiguity, and denial, and run them before adding another capability. You are building the smallest agent project that can teach you something.
