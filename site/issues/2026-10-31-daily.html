Route the work, then verify the result

Multi-model agents are becoming a normal way to trade speed, quality, and cost. The engineering job is to make that trade explicit—and to prove that routing improved the outcome, not just the dashboard.

1. Match effort to the shape of the task

GitHub Copilot Fusion introduces Standard, High, and Max effort levels and can route or orchestrate multiple models for a coding task. Use the cheapest setting that reliably completes your known class of work: routine edits need a different budget from a cross-repository refactor, a security review, or a failing production diagnosis.

Why this matters
Effort levels make an agent’s cost and latency a design choice instead of an accidental property of the prompt.

2. Separate routing quality from model quality

When you evaluate a routed agent, compare it with a fixed-model baseline using the same harness, tools, context, and acceptance tests. Record task success, tool-call errors, time to completion, token or credit usage, and human correction. A routing system can look impressive on aggregate while sending the wrong model to your most important edge cases.

Why this matters
The harness and routing policy can change results as much as the underlying model.

3. Make critique a bounded phase

Multi-model orchestration can use cascades or critique, but critique should have a clear purpose and budget. Ask a second pass to check a small set of invariants—tests, permissions, data handling, and rollback—not to rewrite the whole task. If the critic finds a problem, return a focused finding to the primary agent and keep the final diff reviewable.

Why this matters
Unbounded “have another model look at it” loops consume budget without reliably improving correctness.

4. Preserve the evidence of the route

For important work, record which effort level and models were used, what tools ran, which tests passed, and whether a reviewer changed the output. This makes model upgrades and routing-policy changes auditable. It also gives you a useful training set for deciding which task classes deserve stronger reasoning or a different tool boundary.

Why this matters
Routing only becomes an engineering capability when you can explain and reproduce why a task took the path it did.
Tool spotlight · newly generally available

GitHub Copilot Fusion

What it does: Copilot Fusion routes and orchestrates models for a coding task instead of making the developer choose a single model. GitHub describes Standard, High, and Max effort levels; higher levels can use more than one model for reasoning, generation, debugging, or tool use. Fusion is available in VS Code, the Copilot app, Copilot CLI, and JetBrains IDEs.

Why it was built: Different software tasks need different combinations of speed, reasoning depth, tool use, and review. GitHub built Fusion to make that selection part of the coding harness, so developers can express the task and let the system choose an execution strategy while retaining effort controls and usage visibility.

How to use it: Select Copilot Fusion in the model picker, then choose Standard, High, or Max for the task. Start with a small benchmark of your own issues: one routine change, one debugging task, one refactor, and one security-sensitive review. Compare Fusion against your current default with the same tests and review process. Treat GitHub’s benchmark and cost claims as a reason to measure—not as a substitute for your own data.

One thing to try before lunch

Take ten recent coding tasks and label each routine, investigative, refactoring, or security-sensitive. Run a small sample through two effort levels with identical tests. Track success, review minutes, and cost. Your goal is a routing table grounded in your work—not a universal “best model.”
