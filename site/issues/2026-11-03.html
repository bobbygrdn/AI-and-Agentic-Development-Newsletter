Make failure a first-class tool result

The safest agent is not the one that never encounters an error. It is the one that treats missing policy, failed hooks, and unexpected network effects as explicit stop states.

1. Default to deny when context is missing

Make “settings not loaded,” “approval metadata absent,” and “tool result incomplete” distinct states in your agent runtime. Require the workflow to pause or ask for intervention rather than silently continuing with a permissive fallback. Log which policy version was present at every write boundary.

Why this matters
A missing guard is not evidence that an action is safe.

2. Separate intent from network side effects

Before a web or shell call, show the destination and the data leaving the process—including account identifiers or email addresses that may be embedded in environment context. Put this check in the tool layer, not only in the prompt, and add a test that proves a blocked transmission never reaches the network.

Why this matters
An agent can leak metadata even when its visible answer looks harmless.

3. Make control-plane hooks fail closed

Use a blocking failure mode for approval, policy, security, and audit hooks. Treat hook timeout and hook error as different telemetry, but keep both from authorizing a risky action. Exercise the path with a deliberately failing callback, a slow callback, and a callback that returns malformed data.

Why this matters
A hook that can fail open is part of the attack surface, not a safety control.

4. Review scheduled agents like production services

For background work, test connector scope, revoked credentials, policy reloads, duplicate runs, and a job resuming after interruption. Keep a compact run receipt containing the effective tools, policy hash, model, and final side effects. If the receipt is incomplete, mark the run inconclusive.

Why this matters
Persistence makes stale permissions and unnoticed capability changes harder to see.
Tool spotlight · meaningful update

Claude Code v2.1.317

What it does: Anthropic’s November 3 release adds a warning when a new cloud scheduled task requests unrequested connectors, a check before web or shell calls send an account email address to the network, and an Agent SDK hook option that blocks the action when the callback fails. It also adds notices for managed settings that have not loaded yet, new OTel metrics and cost-reporting support, plus reliability and accessibility fixes.

Why it was built: Long-running and unattended coding workflows need safety signals that are visible at the moment of risk. The update makes capability expansion, network disclosure, policy loading, and callback failure observable instead of letting them disappear into an agent’s internal loop.

How to use it: Upgrade Claude Code, then add onFailure: "block" to approval or security hooks in Agent SDK workflows. Create a test scheduled task that asks for an extra connector and confirm the warning is actionable. Exercise a web or shell call with account context present and verify the network confirmation. Gate writes on managed-settings readiness, and include OTel/cost data in the run receipt. If you still use Opus 4.8 fast mode, migrate and benchmark before its November 30 removal.

One thing to try before lunch

Build a five-case fail-closed fixture suite: missing settings, failed approval hook, unexpected connector, network transmission containing an account identifier, and a revoked credential. For each case, assert both that the side effect is blocked and that the handoff explains what a human must fix.
