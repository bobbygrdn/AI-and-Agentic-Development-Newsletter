Turn agent work into a reviewable workflow

The next step after giving an agent tools is giving its work a durable place to live: a small, inspectable workflow with explicit inputs, constrained permissions, and outputs a human can review.

1. Write the task in Markdown before writing orchestration code

GitHub Agentic Workflows lets you describe repository automation in Markdown and compiles it into a standard GitHub Actions workflow. That makes the task readable in the same place as the repository’s other operating instructions. Start with the trigger, the context the agent may read, the output it should produce, and the conditions under which it must stop.

Why this matters
A reviewable task description gives teammates a chance to improve the workflow before they debug an opaque runner.

2. Prefer reports and draft changes over direct merges

Use agentic workflows for issue triage, CI-failure analysis, dependency reports, documentation updates, and draft pull requests. Keep the default output small and inspectable: a comment, an artifact, or a draft PR. Let a separate human-controlled gate decide whether a change becomes part of the main branch.

Why this matters
Small outputs preserve the speed of automation while keeping the cost of a wrong decision bounded.

3. Treat event text as hostile input

Issue bodies, pull-request descriptions, and comments are user-controlled content. Research on agentic workflow injection found that untrusted GitHub event context can be turned into attacker-influenced behavior when it reaches an agent prompt or tool path. Separate instructions from data, constrain the tools available to the workflow, and test malicious-looking issue text before enabling write access.

Why this matters
Repository automation can be compromised through the work item it was asked to process, not only through the code it checks out.

4. Evaluate the workflow, not just the model

Run a small fixture set that covers normal tasks, ambiguous requests, malformed inputs, prompt injection, permission denials, and partial tool failures. Record whether the workflow stopped, what it wrote, how much review was needed, and whether reruns were safe. Agent performance is a property of the trigger, context, tools, runner, and review gate together.

Why this matters
A workflow that succeeds on a clean demo can still fail at the boundary where real repository events become agent context.
Tool spotlight · general availability

GitHub Agentic Workflows

What it does: GitHub Agentic Workflows is an open-source GitHub Next project for automating reasoning-based repository tasks inside GitHub Actions. A Markdown workflow can call GitHub Copilot or another supported coding agent to handle work such as issue triage, CI failure analysis, documentation maintenance, code review, and reporting.

Why it was built: Many maintenance tasks require repository context and judgment but do not justify a bespoke service. The project turns those tasks into versioned, reviewable workflow files that run where the repository and its normal automation already live. GitHub’s preview design emphasized read-only defaults, sandboxed execution, and a firewall around agent actions.

How to use it: Start from one read-heavy task in a non-critical repository. Install the gh aw extension, create a Markdown workflow describing the trigger, allowed context, tools, and output, then compile or run it through GitHub Actions. Begin with a report or draft PR, inspect the generated workflow and permissions, and add fixtures for prompt injection and rerun behavior before granting any write capability.

One thing to try before lunch

Choose one recurring repository question—“which issues are blocked by failing CI?” is a good start. Define a Markdown workflow that reads issues and Actions runs, writes a report artifact, and never changes code. Test it with an issue containing an instruction aimed at the agent. Your first success criterion is not a clever answer; it is a predictable refusal to treat untrusted text as authority.
