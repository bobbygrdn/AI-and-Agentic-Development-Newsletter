Permission is part of the agent

The useful question is no longer whether an agent can run a command. It is whether the permission model can make the safe path fast while keeping risky actions visible and interruptible.

1. Treat permissions as a control surface

GitHub Copilot’s new Assisted permissions mode uses a language model to evaluate requests to run commands, access filesystem paths, or open URLs. Clearly safe requests can proceed; other requests still require approval. The pattern is broadly useful: put an explicit policy boundary between the agent’s intent and the side effect, rather than relying on a prompt that says “be careful.”

Why this matters
Good permission design reduces approval fatigue without turning convenience into unrestricted execution.

2. Start with a capability inventory

List the actions your agent can take and classify them by reversibility, data exposure, and blast radius. Reading a local file, running a formatter, deleting a directory, opening a production URL, and pushing a release are different capabilities. Give each a named policy, an owner, and a default mode. This makes a vague “agent safety” goal testable.

Why this matters
Agents are easier to supervise when the dangerous part is a small, explicit set of capabilities.

3. Make the model prove the request is safe

Assisted permission checks should be treated as a convenience layer, not as your only security boundary. Log the original request, the command or path, the policy decision, and the resulting outcome. Add deterministic deny rules for secrets, production credentials, destructive commands, and network destinations that should never be reached from a coding session.

Why this matters
A model can help triage routine approvals, but only deterministic controls can guarantee that a known-dangerous action stays blocked.

4. Evaluate model changes against the harness

GPT-6.1 Terra is now generally available in GitHub Copilot, and OpenAI describes it as optimized for fast, capable computer use and agentic coding. When a new model lands in an agent harness, rerun the same task set: tool selection, permission requests, patch quality, test behavior, latency, and cost. A stronger model may change the shape of your approvals even when the tool interface stays the same.

Why this matters
Model upgrades change agent behavior, so they belong in regression testing rather than silent configuration drift.
Tool spotlight · newly generally available

GitHub Copilot Assisted permissions

What it does: Assisted permissions is a permission mode in GitHub Copilot CLI, the Copilot app, and Visual Studio Code. When Copilot asks to run a command, access a filesystem path, or open a URL, a language model evaluates the request. Clearly safe requests can proceed automatically; other requests wait for the developer’s approval.

Why it was built: Fully manual approval slows down routine agent work, while “allow all” makes the session’s blast radius hard to reason about. Assisted permissions is designed as a middle path: automate low-risk decisions while retaining human control over ambiguous or sensitive actions. Enterprise administrators can keep Assisted available while blocking Allow All, or disable Assisted separately.

How to use it: In Copilot CLI, run /permissions and select Assisted. In the Copilot app, open the mode picker, choose Tool permissions, then select Assisted. In VS Code, open the permissions picker and select Assisted permissions. Begin with a repository-local task and inspect which requests are auto-approved; pair the mode with deterministic deny rules, audit logs, and a test suite for sensitive paths.

One thing to try before lunch

Run one small coding task in Assisted mode and record every permission request. Mark each as read, write, network, destructive, or secret-adjacent. Convert the risky categories into explicit deny or approval rules, then rerun the task. You are building a permission contract from observed behavior instead of guessing what the agent will need.
