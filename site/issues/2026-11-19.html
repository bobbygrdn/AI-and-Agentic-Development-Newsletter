Replace polling with events

Agentic workflows lose time and reliability when they repeatedly ask whether something changed. The better pattern is event-driven waiting, bounded subscriptions, and a reviewable receipt for every transition.

1. GitHub Event Streams give agents a cleaner wait state

GitHub’s Event Streams preview lets integrations receive pull-request updates instead of polling. The GitHub CLI 2.105.0 release adds gh event commands that create a subscription, open a stream, and print events as JSON.

For an agent, this changes the control loop: submit a change, subscribe to the smallest relevant event set, wake only on a state transition, then fetch checks and review context. Make the subscription lifetime, event types, and timeout explicit. If the stream ends, record whether the cause was completion, cancellation, expiry, or transport failure.

Why this matters: Event-driven waiting reduces wasted API calls and makes “what woke the agent up?” inspectable.

2. Make the event payload part of the handoff

An event is a trigger, not a conclusion. A pull-request review event can arrive while checks are still running; a state change can be followed by another update before an agent acts.

Use the event to identify the resource, then re-read authoritative state before deciding. Include the event type, delivery time, resource URL, current commit, checks summary, and next allowed action in the handoff. Deduplicate by delivery or resource version where possible, and treat stale events as harmless no-ops.

Why this matters: Re-reading current state prevents agents from acting on an old snapshot or treating a notification as proof that work is complete.

3. Adaptive review should change effort, not standards

GitHub’s Copilot code review update adds adaptive review effort and AI-assisted secret detection capabilities. GitHub’s documentation says Adaptive can choose review effort based on pull-request complexity and risk.

The useful design principle is risk-based effort with a stable acceptance bar. Keep deterministic checks, required security checks, and ownership review constant. Let the agent spend more reasoning or analysis on high-risk diffs, while keeping low-risk changes fast. Measure escaped defects, reviewer overrides, review latency, and false positives rather than counting comments.

Why this matters: A faster review is valuable only when it preserves the checks that protect the repository.

4. Tool descriptions and external content remain untrusted input

Current MCP security guidance continues to call out prompt injection, tool poisoning, confused-deputy behavior, token passthrough, and session-hijacking risks. The MCP security best-practices guidance and MCP security documentation both emphasize that a tool server does not make an agent’s actions safe by itself.

Keep permissions outside natural-language instructions: use allowlists, scoped credentials, typed arguments, server-side authorization, and approval gates for externally visible or irreversible actions. Treat fetched issue text, documentation, repository files, tool descriptions, and event payloads as data to validate, not instructions that can rewrite policy.

Why this matters: Event-driven systems can react faster to malicious input, so speed must be paired with a hard authorization boundary.

5. Model choice is now a workflow decision

GitHub’s November release notes list new Copilot model availability, including Gemini 4 Hydrogen, and its weekly update describes additional model surfaces and administrator controls. Availability, billing, retention, and rollout can differ by plan and surface.

Pin the model and effort settings for your evaluation suite. Record provider, model, tool calls, latency, token use, retries, and human corrections. When trying a new model, compare solved-task cost and review burden, not just first-pass code quality. For team use, document data-retention and policy implications before enabling a model broadly.

Why this matters: A model upgrade changes the behavior of the whole agent loop, including cost, permissions, and review load.

Tool spotlight · event-driven agent loops

GitHub CLI 2.105.0 and gh event

What it is: A preview workflow for waiting on GitHub Event Streams, including pull-request changes, from the command line. Events are emitted as JSON so scripts and agents can consume them.

Try it: Update GitHub CLI to 2.105.0 or newer. In a disposable repository, create a test pull request and use gh event listen with a narrow resource URL and only the event types your workflow needs. Pipe the JSON into a small handler that re-fetches the pull request, checks CI, writes a run receipt, and exits after a bounded timeout. Test reconnect, duplicate delivery, cancellation, and an event that arrives before checks finish.

Caveats: Event Streams are in preview, so command names, availability, quotas, and behavior may change. A stream does not replace authorization or current-state reads. Scope subscriptions narrowly, avoid embedding long-lived credentials in scripts, and ensure reconnect logic cannot duplicate an external action. For production workflows, keep a documented fallback for temporary stream failure.

Why this matters: The smallest useful agent loop is often “wait for a verifiable event, re-read state, act once, and leave evidence.”

One thing to try before lunch

Take one polling loop in your automation and write down its event contract: resource, event types, timeout, deduplication key, authoritative re-read, allowed actions, and failure receipt. Replace the loop in a test branch, then compare API calls, latency, duplicate actions, and recovery behavior.
