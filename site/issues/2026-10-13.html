Better boundaries for better agents

The useful question is shifting from “Can the agent write this?” to “What is the safest, clearest job I can give it?” This morning’s releases point toward tighter control, better handoffs, and more deliberate practice.

What changed

1. Treat agent access as part of the design

GitHub’s October 9 Copilot roundup makes local sandboxing generally available across Copilot CLI, the Copilot app, and VS Code sessions using Agent Host. It can limit an agent’s access to files, networks, and credentials. The same update adds local-model discovery in Copilot CLI through /model, using models available from a running Ollama instance.

Why this matters
Permissions are not a postscript to an agent workflow. Start with the smallest filesystem, network, and credential surface that lets the task succeed, then expand only when a test demonstrates the need.

GitHub’s release notes · Copilot agent documentation

2. Make the handoff visible

GitHub’s VS Code releases for September added recurring automations, agent merge, pull-request creation from Copilot, Claude, or Codex sessions, and a more organized Agents window. The pattern is useful even if you use another tool: separate planning, implementation, review, and landing into observable stages, with a human checkpoint before merge.

Why this matters
When an agent’s work is a session you can inspect—not a mysterious one-shot generation—you can compare approaches, recover from failure, and improve the instructions that produced the result.

Read the VS Code release notes.

3. Put the project contract where every agent can see it

Independent practitioner Tim Deschryver reports strong results from a compact AGENTS.md (or tool-specific equivalent) containing the stack, commands, conventions, and recurring mistakes. He pairs that with skills and spec-driven development. The practical version: document how to run tests, what “done” means, which files are sensitive, and how to validate an architectural change.

Why this matters
Every repeated correction is a missing rule. Turning corrections into durable project guidance makes the next agent session cheaper and more consistent.

The workflow write-up · AGENTS.md reference

4. Practice with a small, measurable loop

JetBrains’ 2026 developer survey says 90% of professional developers surveyed used AI coding agents at work at least weekly, and 68% used them daily. Those are adoption signals, not proof of quality. For improvement, choose one bounded task each week: write a short spec, ask an agent for a plan, let it implement behind a test boundary, review the diff, and record the failure mode you want to prevent next time.

Why this matters
Agentic development is a skill built through feedback. A small loop gives you evidence about prompts, tools, models, and review habits instead of relying on vibes.

See the survey and methodology.

Tool spotlight: GitHub Copilot’s October 2026 agent controls

What it does. The October 9 update bundles three practical changes: generally available local sandboxing for agent sessions, local-model discovery in Copilot CLI via /model, and side-by-side agent sessions in VS Code 1.141. It also adds worktree cleanup so inactive sessions do not quietly consume disk.

Why it was built. Agents now operate across more accounts, environments, repositories, and models. GitHub’s stated focus is control over what agents can access and how their work is managed. That is a response to the operational problems that appear when “just let it code” becomes a team workflow: excess permissions, stranded worktrees, unclear session state, and model choice hidden from the developer.

How to use it.

  1. Update Copilot CLI or VS Code to a current release and start with a disposable branch or worktree.
  2. Turn on local sandboxing and grant only the files, network access, and credentials the task needs.
  3. In Copilot CLI, run /model and compare a local Ollama model with your configured cloud model on a small test task.
  4. For larger work, run two narrow sessions—one for implementation and one for tests or review—then compare diffs before merging.
  5. Clean up inactive worktrees after the task, and keep the successful prompt plus validation commands in the project instructions.

One thing to try before lunch

Add a short “agent contract” to your next repository: goal, allowed files, commands, tests, and stop conditions. Give it to an agent with one issue that can be verified in under ten minutes. The quality of the contract—and the evidence in the diff—will tell you more than a generic productivity benchmark.
