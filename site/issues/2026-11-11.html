Give long-horizon agents a stopping rule

The latest agent releases are pushing software work into longer, more autonomous loops. The practical question is no longer only whether an agent can keep going—it is whether your system can tell when to pause, verify, contain, and hand control back.

1. Gemini 4 Carbon is now available for developer agents

Google made Gemini 4 Carbon available to paying developers on November 10. Google positions it for sustained agentic coding, cybersecurity, scientific reasoning, and other long-horizon work. The Gemini API release notes list a 1-million-token combined input/output window and introductory pricing of $2 per million input tokens and $10 per million output tokens through November 30, 2026; Google’s launch post says the rates then double.

Use a model like this where deeper reasoning can change the outcome: multi-step debugging, architecture audits, or a bounded security review. Start with a fixed repository task and a defined maximum wall-clock time. Capture the plan, tool calls, tests run, unresolved findings, and final diff so you can compare the longer loop with a faster baseline.

Why this matters: A larger reasoning budget is useful only when the workflow has a measurable success condition and a safe exit.

2. Long-running agents need runtime infrastructure, not just bigger contexts

Google Cloud says Agent Substrate 1.0 is generally available on GKE, while Agent Substrate, gVisor, and OpenRL move into CNCF Sandbox status. The design separates stateful agent identity from active compute, snapshots idle sessions, and uses gVisor to isolate untrusted code. CNCF’s November 10 announcement also lists OpenShell as a sandbox project focused on runtime governance and policy enforcement.

For most teams, the immediate lesson is architectural rather than “deploy this today.” Keep agent state external to the worker, make sandbox boundaries explicit, and define what network, filesystem, package-install, and credential access survives a pause or resume. If your agent runs generated code, treat a standard container as a packaging boundary—not automatically a strong isolation boundary.

Why this matters: Persistence increases capability and blast radius at the same time; suspension and isolation are part of the product behavior.

3. Turn deterministic workflows into agent tools

AWS now supports using Step Functions workflows as AI agent tools through Bedrock AgentCore Gateway. An agent can choose when to run a workflow and supply inputs, while Step Functions executes the defined steps in order. Standard AWS and AgentCore Gateway pricing applies.

This is a useful boundary for actions with policy already encoded: refunds, account changes, deployment approvals, or incident remediation. Let the model select among well-described workflows, but keep eligibility checks, approvals, idempotency, retries, and audit events inside the workflow. Return a run ID and status rather than asking the model to narrate success.

Why this matters: Agents are better at choosing the next approved operation than improvising every side effect.

4. Google’s MCP OAuth deadline makes agent identity operational

Google’s Workspace release notes say that, starting November 11, unmarked OAuth clients calling Workspace MCP servers will be rejected; clients still unmarked by November 12 will remain unable to call them. Google recommends separate clients when one integration currently serves both agent and non-agent features. Ordinary Workspace REST API integrations are not affected.

Today, audit any Workspace MCP client you own. Record whether it is truly an agent, its scopes, data domains, approval point, and revocation path. Do not simply mark a shared client to make an error disappear: separating credentials can be the safer design.

Why this matters: Provider policy is becoming part of the runtime contract, so identity and OAuth configuration belong in deployment reviews.

Tool spotlight · generally available November 10

Gemini 4 Carbon

What changed: Gemini 4 Carbon is available through the Gemini API for paying developers, with a long-horizon focus and a 1-million-token combined input/output limit. Google also describes a paid developer path in AI Studio and access through Google Cloud surfaces.

Try it: Pick one reproducible task—such as fixing a seeded bug across a medium-sized repository. Give the agent read-only access first, require a patch plus test output, cap the run by time and tool-call count, and compare it with your current model on correctness, review effort, latency, and total cost. Keep the first result as an artifact, not as an automatic merge.

Caveats: The introductory $2/$10 per-million-token pricing ends November 30 according to Google’s release notes; Google’s launch material says the post-introductory rates double. Long contexts and long decodes can increase spend and review burden even when the final answer looks strong. Model-card benchmarks and vendor claims are not substitutes for your repository’s acceptance tests. Access also varies by product and tier.

Why this matters: The right evaluation unit is a completed, reviewable engineering task—not a model leaderboard score.

One thing to try before lunch

Add a stopping rule to one agent task contract: stop after a fixed budget, after the acceptance tests pass, after two failed repair attempts, or whenever the agent requests a permission outside its allowlist. Require a handoff containing the diff, tests, tool failures, remaining uncertainty, and recommended next action. If the agent cannot produce that receipt, it is not ready for a longer autonomous loop.
