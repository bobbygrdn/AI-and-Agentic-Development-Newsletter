Make agent work reviewable by construction

This week’s developer releases make agents better at choosing models, running repeatable repository work, and operating from a terminal or screen. The engineering lesson is to make every autonomous step produce an artifact a human—or the next tool—can inspect, test, and reject.

The week in practical AI development

1. Model choice is becoming an orchestration problem

GitHub made Copilot Fusion generally available on October 28. Instead of asking developers to pick a model for every task, Fusion routes and, when useful, combines models across Standard, High, and Max effort levels. GitHub reports that Fusion Max scored 60 on the Artificial Analysis Coding Agent Index—within two points of Claude Code with Opus 5.5 Max—at about half the average API cost and tokens and roughly 40% less time per task. Those figures are vendor-reported or benchmark-specific, so teams should measure their own repositories before treating them as a guarantee.

Why this matters
Model selection is now part of application architecture. Define task classes, quality gates, latency budgets, and cost ceilings so routing optimizes the whole workflow—not just the model’s first answer.

GitHub’s Fusion release · Independent reporting from The Indian Express · Independent technical analysis

2. Natural-language workflows are becoming executable repository policy

GitHub Agentic Workflows reached general availability on October 28. Developers describe reasoning-based automation in Markdown; the system compiles it into standard GitHub Actions YAML and runs coding agents for tasks such as issue triage, CI failure analysis, documentation updates, and test writing. Because the result is still Actions, existing runner groups and policy controls remain part of the execution environment.

Why this matters
A workflow prompt is production configuration once it can change a repository. Review it like code: pin dependencies, restrict permissions, test on fixtures, and require a small, auditable output.

GitHub Agentic Workflows announcement · Independent developer analysis · GitHub Actions security and permissions documentation

3. Tool interfaces are widening from APIs to terminals and screens

Google released the gemini-api CLI in beta on October 27 as a stateless, zero-dependency client for agents, scripts, and CI. On October 30, Google also made its Computer Use tool generally available across the Interactions and GenerateContent APIs. The computer-use documentation makes the boundary explicit: your application must run a loop that receives proposed actions, executes them on the client side, and returns the resulting screen state.

Why this matters
When an agent can operate a shell or screen, the client loop becomes a security boundary. Validate actions, keep credentials outside the agent’s reach, and log the before-and-after state instead of trusting a success message.

Google Gemini API release notes · Google Computer Use documentation · Independent Gemini API CLI coverage

4. Agentic development is moving toward explicit lifecycle artifacts

Microsoft’s October 27 guidance on agentic software delivery describes three primitives—Plan, Build, and Verify—with outputs such as acceptance criteria, candidate implementations, and discrete evidence. Android Studio’s October 28 stable release makes “bring your own agent” a first-class workflow, including an agent skills manager and AI code review. Across both announcements, the pattern is the same: agents produce work inside a chain of artifacts rather than replacing the chain.

Why this matters
For your next agent task, define the handoff objects first: goal, constraints, diff, tests, screenshots or traces, and unresolved risks. Better artifacts make review faster and model changes less disruptive.

Tool spotlight: Gemini API CLI

What it does. gemini-api is an open-source beta command-line client for the Gemini API. It is stateless and has no runtime dependencies, so it can be called by coding agents, shell scripts, and CI jobs. It can generate text and media, analyze local files, run managed agents, and expose the underlying Interactions API request shape when a simple command is not enough.

Why it was built. Agents need a predictable interface they can invoke without a full SDK project or a long-lived interactive session. A small CLI makes Gemini capabilities composable with existing Unix pipelines, repository automation, and other coding agents while keeping the application responsible for state and permissions.

How to use it.

  1. Create a billed Gemini API key and expose it to the process as GEMINI_API_KEY or GOOGLE_API_KEY; do not commit it or pass it through untrusted prompts.
  2. Install a pinned beta release using the official CLI guide, or use the documented Go installation path. Pin the version in CI because the command surface is still evolving.
  3. Start with a read-only task such as analyzing a PDF or summarizing test logs, and request structured output when another command will consume the result.
  4. For repository work, have the agent produce a plan and a patch proposal first. Keep file writes, package installation, and network access behind explicit application-side controls.
  5. For managed-agent or computer-use tasks, implement the continuation and client-action loop yourself. Validate every proposed action and record the returned evidence.
  6. Measure usefulness on your own fixture set: correctness, latency, token cost, failure recovery, and the amount of human review required.

A good first experiment is a CI triage helper: pass a failed test log and the relevant diff, ask for a JSON diagnosis with confidence and next checks, then require a human to approve any issue comment or code change.

One practice to take into next week

Turn one recurring maintenance task into a four-stage pipeline: plan, act, verify, report. Give the agent a narrow permission set and require a machine-readable result at each boundary. If a stage cannot explain what it changed and how it checked the change, it is not ready to run unattended.
