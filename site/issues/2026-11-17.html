Make the handoff the unit of agentic work

Agents are getting better at producing patches. The engineering advantage now comes from making each handoff easy to inspect: what changed, what was tested, what remains uncertain, and who owns the next decision.

1. Agentic engineering is a workflow, not a faster autocomplete

GitHub’s guide to agentic engineering argues that the work now spans planning, implementation, review, and production investigation. It also cites Faros AI’s finding that pull requests spent 441% longer in review as teams moved from low to high AI adoption.

That is a useful design constraint. Give every agent task a compact handoff contract: objective, files touched, commands run, test results, known limitations, and a suggested reviewer focus. If the contract cannot be filled, the task is not ready to leave the agent loop.

Why this matters: Faster generation can simply move the bottleneck into review; a structured handoff makes the new work legible.

2. GitHub’s latest Copilot changes favor continuity and model choice

GitHub’s November 9 weekly release adds GitHub Enterprise Server repositories to the Copilot app, lets users re-authenticate MCP servers in place, and adds Claude Fable 5.2 and Gemini 4 Carbon to the available model set. GitHub also notes that rollout and policy availability vary by plan.

Use the new options as an experiment, not as a silent default change. Run the same small fixture through your existing model and one alternative; compare successful completion, tool calls, latency, review findings, and total spend. Record the model and policy state in the handoff so a later reviewer can reproduce the result.

Why this matters: More models and connected tools increase capability, but they also increase the number of changing variables in a development workflow.

3. Durable cloud agents make recovery part of the product

OpenAI’s Agents API describes a managed Codex harness for durable cloud agents, including sessions, orchestration, context compaction, recovery, sandboxes, code execution, and MCP connections.

The practical lesson is to make recovery observable. Persist the task specification, tool calls, checkpoints, approvals, and final artifact separately from the model transcript. Add a resume test that stops an agent after a tool failure and verifies it can continue without repeating an irreversible action.

Why this matters: Long-running agents fail in the middle, so “can it resume safely?” is as important as “can it finish once?”

4. New model releases are a reason to re-run evals, not rewrite prompts

Anthropic announced Claude Fable 5.2 and Claude Mythos 5.2 on November 9 as models aimed at demanding technical work. GitHub’s release notes show how quickly such models can enter developer tools.

Keep prompt changes and model changes separate. Freeze a representative task set, run the old and new model under the same tool permissions, and score both the functional result and the handoff quality. Include negative tests: ambiguous requirements, missing credentials, failing tests, and requests that should be refused.

Why this matters: A model upgrade can improve capability while changing refusal behavior, cost, latency, or the shape of failures.

5. Security evidence has to travel with the patch

Independent coverage collected by New Runtime highlights a November 11 GitGuardian finding of exposed secrets in Claude Code project settings files across public repositories. The specific product and counts should be checked against the underlying report before being used as a benchmark, but the engineering lesson is immediate: local agent configuration is source material and must be treated like code.

Keep project-level settings out of commits when they contain credentials or machine-specific permissions. Add secret scanning to the agent handoff, document the effective tool and network policy, and require a clean scan before merge. A successful test suite does not prove that the patch is safe to share.

Why this matters: Agent workflows create new configuration surfaces where secrets and permissions can leak before application code is even reviewed.

Tool spotlight · durable agent execution

OpenAI Agents API

What it is: A hosted way to build durable agents around the Codex harness, with managed sessions, orchestration, context compaction, recovery, sandboxes, tools, and artifacts.

Try it: Start with one bounded workflow—such as comparing two release-note files and producing a change summary. Give it a disposable sandbox and read-only inputs. Persist a run receipt containing the task ID, model, tool calls, files read, output artifact, tests or checks performed, and any recovery event. Then force a failure midway and verify that resume does not duplicate a side effect.

Caveats: Model usage, OpenAI tools, and hosted sandboxes are billed separately according to the platform’s pricing rules. Managed orchestration reduces infrastructure work but does not remove your responsibility for tool permissions, data residency and retention choices, prompt-injection defenses, or approval gates. Treat recovery as a behavior to test, not a guarantee to assume.

Why this matters: A durable agent is useful only when its progress, permissions, and recovery path remain reviewable.

One thing to try before lunch

Take one existing coding-agent task and add a required handoff file with five fields: goal, changed files, verification run, remaining uncertainty, and next reviewer question. Run the task once, then ask a second agent or teammate to review only the handoff and patch. If they cannot identify the risk without reopening the entire transcript, improve the contract.
