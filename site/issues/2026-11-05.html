One harness, explicit tradeoffs

Agentic development is becoming a model-selection problem, a context problem, and a cost problem at the same time. Keep the workflow stable while you make those tradeoffs visible.

1. Keep the task contract independent from the model

Write the task, acceptance tests, tool permissions, and handoff format once. Then let the harness choose among models or providers behind that contract. Record the selected model, effort setting, and reason so a later review can explain why the run took the path it did.

Why this matters
Portability is useful only when changing a model does not silently change the job.

2. Route by task shape, then verify the route

Classify work by latency sensitivity, context size, risk, and expected iteration count. Use a fast or lower-cost model for routine transformations, and reserve deeper reasoning for changes that touch security, data, incidents, or public behavior. Compare every route against a fixed-model baseline.

Why this matters
Adaptive routing can save money, but only a baseline tells you whether the savings came with hidden quality loss.

3. Treat cost as a property of the whole loop

Measure retries, tool calls, context reloads, review time, and rework—not only input and output tokens. For asynchronous work, compare cost per accepted change and cost per reverted change. Keep an explicit budget for the human review that makes the agent’s output shippable.

Why this matters
The cheapest generation is not the cheapest delivery if it creates a longer review queue.

4. Make provider changes reversible

Keep original settings backed up, use a dry-run path, and define an off switch for every routing layer. Test a task on the old and new path with the same fixture, tools, and repository state. Store the route receipt with the change so regressions are diagnosable.

Why this matters
Agent infrastructure should fail back to a known workflow instead of trapping the team in an opaque configuration.
Tool spotlight · newly released

Fireworks Nexus Desktop

What it does: Fireworks’ Nexus Desktop brings open models into the Codex app, Claude Desktop, and OpenCode, with model selection and centralized spend visibility. The November 3 launch is part of a broader Nexus release that also adds the Nexus CLI and model-serving options for teams that want to match inference speed and price to different workloads.

Why it was built: Developers increasingly use several AI tools, but switching models can mean changing subscriptions, settings, and observability. Nexus is designed to keep the familiar coding or coworking surface while giving teams more model choice and a way to see spending across that choice.

How to use it: Start with a small, non-production repository. Connect one harness, pick a single open model, and run a fixed fixture suite against your current default. Compare correctness, tool-call count, latency, and total spend—not just tokens. Then add a second model for a distinct task shape and document the routing rule. Use the Nexus CLI only after you have a rollback path; its documented nexus <harness> off command restores the original harness settings.

One thing to try before lunch

Choose one recurring coding task and run it three ways: your current model, a lower-cost model, and a deeper model. Keep the prompt, tools, repository snapshot, and acceptance test fixed. Report cost per accepted change, wall-clock time, and review effort. That table is the beginning of an honest routing policy.
