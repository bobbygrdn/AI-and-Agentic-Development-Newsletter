Make the agent's defaults visible

A capable agent can still waste time, overspend, or create security debt when its defaults are hidden. Treat effort, compaction, subagent behavior, retries, and permissions as versioned engineering policy.

1. Turn defaults into a checked-in policy

Record the model, effort ceiling, context window, compaction behavior, retry limit, tool allowlist, and write boundary for each workflow. Put the policy next to the code or workflow definition. If a client silently changes a default, your evals and reviews should show the change.

Why this matters
Invisible defaults turn a reproducible engineering process into a moving target.

2. Give subagents an explicit budget

When a parent agent delegates, specify the subagent’s task, effort level, maximum turns, allowed tools, and return format. Do not let every worker inherit the strongest setting automatically. Use a cheap worker for retrieval or classification and reserve high effort for the narrow decision that needs it.

Why this matters
Budgeted delegation controls cost and makes failures attributable instead of producing an untraceable swarm.

3. Test the recovery path, not just the happy path

Add fixtures for rate limits, failed commands, stale context, partial tool results, interrupted sessions, and a reviewer who rejects the proposed change. Measure whether the agent stops safely, preserves state, and returns a useful handoff. A run that succeeds only when every tool behaves perfectly is not production-ready.

Why this matters
Agents spend real time in the edges between tools, sessions, and approvals.

4. Review policy changes like code changes

Require a diff and a small regression suite when changing permissions, effort defaults, compaction, or retry logic. Include cost and security checks in the review. For a coding agent, a one-line policy change can alter every future patch more than a one-line implementation change.

Why this matters
The control plane is part of the product, so it deserves the same ownership and rollback discipline.
Tool spotlight · meaningful update

Claude Code v2.1.316

What it does: The October 31 release adds controls for subagent effort, pooled group budgets, layered policy modes, guardrail input tagging for Bedrock, and several reliability and accessibility fixes. It also changes ultrathink to request xhigh effort on supported models and deprecates fast mode for Opus 4.8 ahead of its November 30 removal.

Why it was built: Long-running coding agents need stronger operational controls than a model selector alone. Shared budgets, layered policies, explicit subagent effort, and safer gateway behavior help teams manage spend, governance, and predictable execution across local, cloud, and enterprise environments.

How to use it: Upgrade Claude Code, then inspect the release notes against your organization’s policy. Set a deliberate default for subagents with CLAUDE_CODE_SUBAGENT_EFFORT; configure pooled budgets only after deciding the team-level cap; and test layered policy mode with a read-only fixture before enabling writes. If you rely on Opus 4.8 fast mode, migrate and benchmark Opus 5.5 before November 30. Keep a small suite that checks permissions, retries, compaction, and interrupted-session recovery.

One thing to try before lunch

Copy your agent’s current defaults into a short policy file. Mark each as intentional, inherited, or unknown. Then add one regression task for each unknown: a subagent call, a failed tool, a retry, a compaction boundary, and a rejected write. The goal is not more configuration; it is fewer surprises.
