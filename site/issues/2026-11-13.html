Treat agent skills like software

The fastest way to make agentic development more dependable is to move important behavior out of the chat transcript and into reviewable software: versioned skills, explicit tool contracts, portable traces, and tests that prove the agent stopped when it should.

1. GitHub’s agent-skills guidance turns repeated instructions into a team asset

GitHub’s new practical guide describes an agent skill as a versioned directory centered on a SKILL.md file. The useful separation is simple: the skill carries reusable procedure and project conventions, while the host still supplies tools, credentials, permissions, and runtime context.

Start with the task you explain repeatedly. Write the smallest discoverable description, keep detailed instructions and scripts behind the task boundary, and add checks for the decisions that need human judgment. Put repository-specific names and schemas in a manifest rather than duplicating them across skills. Treat the skill like code: review it, test it with another agent, and change it through normal version control.

Why this matters: A skill can preserve institutional knowledge without silently becoming a new authority layer.

2. MCP and Agent Skills are converging, but portability still needs governance

Google’s November 11 update says MCP and Agent Skills are being co-maintained under the Linux Foundation’s Agentic AI Foundation. MCP connects agents to live tools and data; skills provide procedural knowledge on demand.

That division is useful for architecture. Keep tool schemas narrow and capability-focused; keep procedures portable and host-aware; bind both to explicit identity, approval, and audit rules. Before installing a third-party skill, inspect its scripts, network calls, credential assumptions, update provenance, and requested tool permissions. “Portable” should not mean “trusted by default.”

Why this matters: Shared standards reduce integration work, but they also make supply-chain review a routine engineering responsibility.

3. Agent evaluation is becoming a lifecycle discipline

AWS’s Agent DLC guidance frames agent delivery as one lifecycle with two loops: improve the agent and verify that each change actually improved the system. Its warning is familiar to anyone who has shipped an agent: an aggregate score can rise while coverage, tool choice, or safety gets worse.

Apply the pattern with a small canonical run record: task fixture, prompt or skill version, model, tool calls and arguments, handoffs, policy decisions, latency, cost, tests, and final outcome. Compare the same fixtures before and after every meaningful change. Keep quality, safety, latency, and spend visible separately instead of compressing them into one “agent score.”

Why this matters: The right unit of progress is a repeatable run with evidence, not a better-looking demo.

4. Trace monitoring can catch misuse that output checks miss

Google’s Agent Anomaly Detection uses OpenTelemetry traces and logs to flag goal hijacks and tool misuse asynchronously. Google reports 87% detection on five public security benchmarks; that is a vendor-reported result, not a guarantee for your workload.

Use the idea defensively: record the intended goal, allowed tools, expected sequence, and high-risk transitions, then alert on deviations such as unexpected network access, privilege changes, repeated retries, or tool calls outside the task’s scope. Keep runtime allowlists and approvals in place; anomaly detection is a second layer, not authorization.

Why this matters: A plausible final answer can hide a dangerous path taken to produce it.

5. Long-running agents need an explicit definition of “done”

AWS’s recent agent lifecycle work and its broader guidance on feedback point toward the same operational rule: an agent should not be allowed to optimize forever. Give every autonomous loop a budget, a stopping condition, and a handoff format.

Make “done” testable: all required checks pass, no unresolved high-risk tool result remains, the agent has recorded what it did not verify, and a human or deterministic workflow owns the next side effect. Persist a compact receipt so another engineer can resume or reject the work without replaying the entire transcript.

Why this matters: A bounded agent is easier to debug, price, interrupt, and trust.

Tool spotlight · announced November 11

Amazon Bedrock AgentCore Web Search API

What changed: AWS announced a Web Search API that lets application code search the web through a signed API call, using AWS SDKs or the CLI, without creating a gateway or separate search resources. It is designed for applications, agent loops, and data pipelines.

Try it: Put web search behind one narrow application function with a typed request: query, allowed domains, freshness window, maximum results, and citation requirement. Log the request, returned sources, timestamp, and downstream claims. Start in a read-only research workflow; require a separate approval before search results can trigger writes, messages, deployments, or purchases.

Caveats: Search results are evidence, not truth. Add domain allowlists for high-stakes workflows, defend against prompt injection in retrieved pages, cap query volume and spending, and preserve citations with the generated output. Review AWS regional availability, authentication, quotas, and pricing before production use; a signed call authenticates the client but does not validate the content it retrieves.

Why this matters: A governed search primitive is easier to audit than giving every agent an unconstrained browser, but it still needs content-level defenses.

One thing to try before lunch

Choose one repeated agent task and create a tiny “agent contract” beside it: the skill version, allowed tools, maximum turns or cost, stop conditions, required tests, and handoff receipt. Run the task twice—once with the contract and once without it. Compare not only the answer, but the tool path, time, spend, and what a reviewer can verify.
