Make agent quality repeatable

AI-assisted development is moving from impressive demos to repeatable team workflows. The practical shift is to test agent behavior like software, scan its changes for secrets, and budget the infrastructure that keeps sessions alive.

1. GitHub Copilot Evals turns customization into a testable change

GitHub Copilot Evals is now in public preview. It lets developers create repeatable tests for a skill, custom agent, or MCP tool, then compare runs before and after a change. GitHub says the eval engine is Vally, an extensible local evaluation tool, and that each run is approved before it starts.

Start with three to five realistic tasks, not trivia. Define a pass condition that can be checked from the result and the path taken: files changed, tests run, tools called, and forbidden actions avoided. Keep a small baseline in the repository and rerun it after changing prompts, models, skills, or MCP configuration.

Why this matters: One successful agent run is anecdotal; a stable task set gives you evidence that a customization improved rather than merely changed behavior.

2. Secret scanning now belongs inside the agent loop

GitHub’s secret-scanning update adds provider-pattern detection to Copilot’s security review specialist when enabled. GitHub says the public preview covers Copilot CLI, the Copilot app, SDK integrations, and Copilot code review, with more than 500 secret types in the catalog.

The control is opt-in and scans consume AI credits under the Secret Protection AI Credit SKU. For SDK integrations, GitHub documents an important boundary: a model-provider API key alone is not sufficient; the integration needs GitHub authentication, and VS Code is not included in this release.

Use secret detection as a merge gate or pre-merge review step, but keep ordinary repository secret scanning and credential rotation in place. Detection is not remediation: revoke exposed credentials first, then clean history and verify the fix.

Why this matters: Agents increase the number of generated edits, so preventing credential leakage must be automatic, explicit, and independent of the model’s own judgment.

3. Background work needs a cost and cancellation contract

OpenAI’s November API changelog lists two-hour and eight-hour background completion windows in public beta, priced below Standard rates for those windows. Longer-running work can be useful for repository analysis or batch maintenance, but a lower token price does not make an unbounded workflow cheap.

Before enabling background execution, record the task budget, maximum wall-clock time, cancellation path, retry policy, and the evidence required for completion. Make the agent produce an intermediate receipt before it attempts an external side effect. Track cost per solved task, not just tokens or time spent running.

Why this matters: Persistence changes the failure mode from “the request timed out” to “the system kept acting,” so cancellation and evidence become product features.

4. Agent sessions are not ordinary web requests

Google’s GKE guidance describes coding agents as long-lived sessions that may wait between prompts. That creates different scheduling and cost behavior from short web requests, because capacity can remain allocated while an agent is idle.

If you run agents on shared infrastructure, separate active execution from waiting state where possible. Measure session occupancy, useful work time, queue delay, restart recovery, and cost per completed task. A session-aware design may use suspend/resume, smaller pools, or explicit expiration rather than leaving every agent attached to a full-size node.

Why this matters: The unit you pay for may be a session, not a request, and idle agent time can quietly become the largest line item.

5. MCP access is becoming an explicit product decision

Google Workspace’s developer release notes say Workspace MCP servers now require OAuth clients to be marked for use by an AI-powered agent. Google also recommends separating an agent client from a client used for non-agent features when both exist.

That is a useful pattern beyond Google Workspace: give agentic integrations their own client identity, scopes, audit trail, and revocation path. Review each tool’s read and write capabilities, and make the user-visible consent language match the actual actions the agent can take.

Why this matters: Separate identities make it possible to apply agent-specific policy without weakening ordinary integrations.

Tool spotlight · repeatable agent evaluation

GitHub Copilot Evals

What it is: A public-preview workflow for evaluating Copilot skills, custom agents, and MCP tools against realistic tasks, with pass/fail checks and before-and-after comparisons.

Try it: Install the GitHub Copilot Evals extension in VS Code, the plugin in Copilot CLI, or the github/evals marketplace in the Copilot app. Pick one workflow you already trust, write a small task fixture, define observable checks, run the baseline, change one variable, and compare the results. Include at least one negative test, such as a prompt injection in repository content or an attempt to call a tool outside its allowlist.

Caveats: It is public preview, so commands and supported surfaces can change. Evals measure the tasks and checks you write; they do not prove general safety. Runs require approval, and a passing result should not replace human review for high-impact changes. Keep fixtures free of production secrets and avoid evaluating against data the agent should not retain.

Why this matters: A small, versioned eval suite is the fastest way to turn “the agent feels better” into a decision you can revisit.

One thing to try before lunch

Create a single agent regression fixture: task, starting repository state, allowed tools, expected artifacts, forbidden actions, and pass/fail checks. Run it three times before changing anything. Then change one prompt, model, skill, or tool permission and compare solved-task rate, review effort, latency, and cost.
