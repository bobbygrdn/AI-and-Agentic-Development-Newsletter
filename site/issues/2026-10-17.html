Keep the agent interruptible

The week’s most useful lesson is not “make the agent more autonomous.” It is to shorten the distance between action, evidence, and correction. Steer while work is moving, predict failures before expensive runs, and treat review capacity as a hard engineering budget.

The week in one control loop

1. Course-correct before the turn is over

OpenAI’s stable Codex CLI 0.163 release, published October 15, lets a developer send a follow-up while Codex is responding. A new instruction can steer the running turn immediately; interrupting also stops active Code Mode cells and nested tool calls. The same release adds searchable in-session configuration and parallel execution for independent read-only lookups.

Why this matters
Long agent runs should not turn a mistaken assumption into sunk cost: make checkpoints visible and correct direction as soon as new evidence appears.

OpenAI release notes, October 15 · Independent practical overview, updated October 17

2. Predict the failure mode, not only the score

A newly revised preprint from researchers at the University of Virginia, Microsoft Research, and Tsinghua adds an Improvement Dynamics Model to a self-modifying agent. Before an expensive evaluation, the model predicts task-level outcomes—including the difference between a wrong answer and a run that never finishes—and can give the modifying agent one more revision. The authors report gains across coding, paper review, robot-reward design, and math grading, including under matched token budgets.

Why this matters
Before an agent changes its own prompt, tools, or code, ask it to forecast concrete regressions and name the evidence that would falsify the change.

Primary paper, revised October 15 · Tech Xplore explanation, October 16

3. Optimize the queue after generation

A Harvard study covering 300 million work events across 718 firms found that agent adoption raised lines of code by 30%, commits by 20%, and pull requests by 23%, but did not produce a statistically significant increase in resolved Jira issues or epics. Review time rose 49%; change requests nearly doubled; comments per pull request rose 35%. The authors describe review as the bottleneck that absorbs much of the coding-speed gain.

Why this matters
Agent throughput is useful only when verified work ships; cap pull-request size, require task-specific tests, and budget reviewer time before increasing parallelism.

Primary study, August 4 version · Ars Technica analysis, October 9

4. Make every handoff evidence-shaped

Taken together, the releases and research point to a practical agent contract: state the goal and boundaries; require a plan; make assumptions interruptible; run cheap checks before broad tests; and return a compact evidence bundle—diff summary, tests run, failures, risks, and unresolved questions. Reviewers should not have to reconstruct the agent’s path from a large patch.

Why this matters
A small, structured evidence bundle converts agent output from “code to inspect” into “claims to verify,” reducing both review latency and missed defects.

Tool spotlight: Codex CLI 0.163

What it does. Codex CLI is a terminal coding agent that can inspect a repository, edit files, run tools, and collaborate through a threaded interface. Version 0.163 adds mid-response follow-ups, a searchable /config panel, a configurable leader key through /keymap, restart controls for its managed background server, and parallel independent read-only lookups.

Why it was built. Long-running coding work needs a control surface, not just a better first prompt. This update reduces the cost of changing direction, exposes settings without manual configuration-file editing, and speeds safe context gathering while keeping mutating work ordered.

How to use it.

  1. Install or update the CLI using the supported package for your environment, then confirm the version reports 0.163.0.
  2. Open a small repository task and ask Codex to state its plan, assumptions, and validation commands before editing.
  3. While it works, send a follow-up as soon as an assumption changes—for example: “Keep the public API unchanged; add a regression test first.” Do not wait for the full turn.
  4. Use /config to review permissions and preferences in-session. Treat restart-required settings as a deliberate checkpoint.
  5. Let read-only discovery run in parallel, but keep writes narrow: one coherent change, a small diff, and explicit tests.
  6. End with an evidence bundle: files changed, commands run, test results, risks, and the next human decision.

Try it on a bug with one reproducible failure. Give the agent the failing command, interrupt once with a newly discovered constraint, and compare the final review effort with a run where correction waits until the end.

One thing to try this weekend

For one agent task, write four lines before you start: goal, non-negotiable constraint, cheapest falsifying check, and review budget. Interrupt the run when any line changes. That tiny loop is more valuable than another page of prompt instructions.
